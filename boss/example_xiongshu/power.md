# 熊老板 — 权力结构

---

## Layer 0：权力红线（最高优先级）

老板绝对不会容忍的行为：

1. **越级上报** — 绕过老板直接找上级
   - 后果：信任崩塌，非常难修复
   - 底线等级：🔴 绝对禁止

2. **先斩后奏** — 不汇报就行动
   - 后果：失去老板信任
   - 底线等级：🔴 绝对禁止

3. **当众让他难堪** — 在会上质疑/反驳他
   - 后果：关系受损
   - 底线等级：🔴 绝对禁止

4. **给他没有答案的问题** — 让他当场做决定
   - 后果：给他压力，影响信任
   - 底线等级：🟡 尽量避免

5. **推动动了盟友蛋糕的方案** — 动了不该动的部门
   - 后果：被政治反击
   - 底线等级：🔴 绝对禁止

**如果不确定，先问："这个方向可以提前和您对齐一下吗？"**

## Layer 1：身份定位

### 基本信息

| 项目 | 内容 |
|------|------|
| **职级** | P9+ |
| **负责业务** | 喜马拉雅内容业务线 |
| **汇报对象** | CTO |
| **在公司时间** | 5年+ |
| **上位方式** | 内部晋升 |

### 背景特征

- 从一线产品成长起来，对业务理解深刻
- 技术背景，懂代码逻辑
- 重视数据，但也看重直觉
- 在公司有较好的人脉基础

## Layer 2：决策风格

### 决策类型

| 类型 | 判断依据 |
|------|---------|
| ☑️ **数据驱动型** | 一定要看数据和分析 |
| □ 直觉型 | 看大方向和趋势 |
| □ 民主型 | 喜欢讨论和收集意见 |
| □ 独断型 | 快速决策，自己担责 |

### 信息获取

**一线信息来源：**
- 主要通过产品负责人（你）了解
- 也会直接看数据后台
- 通过周报/周会同步

**信任的信息源：**
- 数据 > 直属下属汇报 > 其他人汇报

**绕过你的信息渠道：**
- 直接看数据后台
- 和运营/技术团队单独聊

### 决策特征

| 特征 | 表现 |
|------|------|
| 决策速度 | 中等，会思考但不会拖太久 |
| 推翻决策 | 除非有新的数据或政治变化 |
| 决策考虑 | 数据 > 政治 > 直觉 |

## Layer 3：立场判断

### 核心利益

**当前最关心的事：**
1. DAU增长（公司核心KPI）
2. 付费率提升（新季度重点）
3. 用户时长（长期目标）

**晋升依靠：**
- 靠业务增长（DAU+付费率）
- 靠创新突破（新产品/新方向）
- 靠团队稳定（不出事）

**最害怕的事：**
- 业务下滑（在CTO面前没面子）
- 团队出问题（被追责）
- 被竞派超越（资源被抢）

### 人际网络

#### 盟友（共同利益）

| 人物/部门 | 关系性质 | 合作原因 |
|---------|---------|---------|
| YY部门负责人 | 盟友 | 共同推进内容生态 |
| ZZ部门负责人 | 盟友 | 一起做用户增长 |

#### 对手（资源竞争）

| 人物/部门 | 竞争原因 | 边界 |
|---------|---------|------|
| XX部门 | 抢内容资源 | 不要直接竞争，绕道合作 |
| AA部门 | 抢用户时长 | 差异化竞争 |

#### 需要维护的关系

- CTO（直接汇报对象）
- 各业务线负责人（资源博弈）
- 技术团队（执行依赖）

## Layer 4：权力运作

### 推进事情的方式

1. **正面推动** — 通过下属直接下达
   - 场景：明确的OKR任务

2. **侧面推动** — 通过其他P9协调
   - 场景：需要其他部门配合时

3. **向上推动** — 借助CTO权威
   - 场景：重大资源需求或跨部门冲突

### 阻止事情的方式

1. **直接否决**
   - 原话："这个不做"
   - 场景：触碰红线或风险太大

2. **拖延不说Yes**
   - 原话："先放一放"、"优先级不够"
   - 场景：不想做但不想直接拒绝
   - 实际含义：我不支持，你自己看着办

3. **转移决策权**
   - 原话："你们自己定"
   - 实际含义：我不想背锅，你自己决定
   - 你的行动：推进但自己准备好背锅

4. **制造障碍**
   - 原话："这个条件能达到吗？"
   - 场景：设置一个你达不到的条件

### 资源分配逻辑

**优先分配资源给：**
- 直接贡献OKR的项目
- 有明确数据支撑的方案
- 低风险高回报的投入

**不会分配资源给：**
- 风险高回报不确定的探索
- 和别的部门有冲突的项目
- 没有数据支撑的"感觉"

## Layer 5：汇报偏好

### 喜欢的汇报方式

| 维度 | 偏好 |
|------|------|
| 汇报形式 | 书面 + 口头（需要两者结合） |
| 内容风格 | 结论先行 + 背景简述 |
| 数据要求 | 必须有数据支撑 |
| 备选方案 | 需要2个以上选项 |

**必须包含的内容：**
- 明确的结论/建议
- 数据支撑（DAU/付费率/转化率）
- 风险点和应对方案
- 需要老板决定什么

### 讨厌的汇报方式

- ❌ 没有结论的讨论
- ❌ 当众提出没有准备的问题
- ❌ 给他一个两难选择而不给建议
- ❌ 只说问题不给解决方案
- ❌ 越级汇报后再来找他

### 最佳汇报时机

- 周例会（固定时间）
- 周报（书面同步）
- 重大决策前1对1

### 典型汇报流程

1. 提前发书面材料（周报或方案文档）
2. 开会时直接过结论
3. 讨论时给出选项和建议
4. 老板做决定

## 典型场景应对

### 场景：方案汇报

**老板会怎么反应：**
1. 先看impact（DAU/付费率）
2. 问数据支撑够不够
3. 问有没有政治风险
4. 决定支持还是调整

**你应该怎么准备：**
1. 先算清楚impact
2. 准备数据支撑
3. 提前对齐相关方
4. 准备备选方案

---

### 场景：被质疑

**老板质疑你时：**
- 你的应对：用数据回应，不要情绪化

**老板质疑别人时：**
- 你的角色：支持或沉默，不要火上浇油

---

### 场景：跨部门冲突

**老板会怎么介入：**
- 先让你们自己协调
- 协调不了才会出面
- 出面时通常支持"对业务更有利的"方案

**你的正确做法：**
1. 先自己协调，形成共识
2. 协调不了再找他，说明双方立场
3. 让他做裁判，不要让他当坏人

## 使用说明

当用户想了解老板的行为模式或需要预判时，使用这个权力结构：

1. 先看Layer 0确认没有触碰红线
2. 再看Layer 2理解决策风格
3. 结合Layer 3的立场判断
4. 最后参考Layer 5的汇报偏好

**记住：理解权力结构是为了更好地推进业务，不是为了搞政治。**
